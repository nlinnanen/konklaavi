HashTrust

Users flag web content as malicious, as propaganda, or as AI slop. The system combines these flags into a reputation for each site, page, and comment. A Chrome extension then warns the next user who opens that content, and gives the reason.

Three work areas: the extension, the reputation model, and the backend.

How the system works

The system keeps two reputations. Target reputation controls what users see. User reputation controls how much each flag counts. Each reputation is an input to the other.

  1. User A opens a page and sends a flag. The flag names a target and a label.
  2. The backend stores the flag. The reputation engine multiplies the flag by the weight of User A.
  3. The engine adds the weighted flags for each label. The result is the target reputation.
  4. When the target reputation for a label is above a limit, the target gets a warning.
  5. User B opens the same target. The extension shows the warning with the label and the reason.
  6. User B can confirm the warning or dispute it. proposed
  7. The engine compares each flag with the consensus on its target. Users who agree with the consensus gain reputation. Users who disagree lose reputation.

Terms

This document uses each term with one meaning.

User
A person who has the extension and an account.
Target
The content that a flag names. A target is a domain, a page, or a comment.
Label
The type of problem: malicious, propaganda, or AI slop.
Flag
One report from one user. A flag names one target and one label.
Dispute proposed
One report from one user that says a label is wrong for a target.
Target reputation
One score for each label on a target. The team description calls this site reputation.
User reputation
One score for each user. This score sets the weight of the flags from that user.
Consensus
The result for a label that most of the weight on a target supports.
Verdict
The result that the extension receives for a target: warning or no warning, with the label and the reason.

Targets: domain, page, comment

A flag names the most specific target that the user selects. The engine keeps a separate reputation for each target.

The warning applies at the level where the flags concentrate. Flags on many pages of one domain give a warning for the domain. Flags on one page give a warning for that page only.

Comments are targets only on integrated sites. For each integrated site, the extension needs an adapter that finds the comments and reads a stable ID for each comment.

Components

The project has three work areas. Figure 3 shows the data flow between them. The lists below give the job of each component.

Extension

Popup
The popup shows the flag form. The user selects a label and a target level, then sends the flag.
Warning
The content script shows a warning when the target has one. The warning states the label and the reason, for example the number of users who flagged the target.
Confirm and dispute proposed
The warning has two buttons. The user confirms the label or disputes it. Without a dispute, the model cannot see disagreement.
Site adapters
Each integrated site needs one adapter. The adapter finds the comments on a page and reads the ID of each comment. It marks the comments that have a warning.
Service worker
The service worker sends flags to the API. It requests the verdict for each URL that the user opens. It keeps recent verdicts in a local cache.
URL rules
These rules convert a URL to a domain target and a page target. They remove tracking parameters and fragments. The backend must use the same rules.
Account
The extension authenticates the user. The backend needs one stable identity for each flag.

Reputation model

Target scoring
This job calculates one score for each label on each target. Flags increase the score and disputes decrease it. The weight of the user scales each flag and each dispute.
Level rule
This rule selects the level that gets the warning: domain, page, or comment.
Verdict rule
This rule converts a score to a verdict. A warning needs a score above a limit and flags from a minimum number of different users.
User reputation update
This job compares each flag with the consensus on its target. Agreement increases the reputation of the user. Disagreement decreases it.
Collusion detection
This job finds groups of users who agree with each other but disagree with other users. It decreases the reputation of each member.
Time decay proposed
Old flags lose weight with time, because a site can change.

Backend

API
The API receives flags and disputes, and returns verdicts. It authenticates each user and limits the request rate.
Event log
The log stores every flag and every dispute. It never changes a stored event. After a change to the model, the engine can calculate all scores again from the log.
Reputation worker
The worker runs the three engine jobs. Target scoring runs on each new flag. The user reputation update runs when the consensus on a target changes. Collusion detection runs at a fixed interval.
Verdict store
This store holds the current scores and the verdict for each target. The API reads from it on each verdict request.
User store
This store holds accounts, user reputation, and the penalties from collusion detection.
Hosting
The hackathon requires a public deployment on Hostinger infrastructure. One server can run the API, the worker, and the database. proposed

Reputation model

Target reputation

Each target has one score for each label. A flag adds the weight of its user to the score. A dispute subtracts the weight of its user.

A target gets a warning when two conditions are true:

  • The score for a label is above the limit.
  • Enough different users contributed to the score.

The second condition prevents a warning that comes from one or two users with a high weight.

User reputation

Each user has one reputation score. The score sets the weight of every flag and every dispute from that user.

The engine updates the score when a target reaches a stable consensus. A user who agreed with the consensus gains reputation. A user who disagreed loses reputation.

A user who frequently flags content that other users find acceptable therefore loses weight with time.

Collusion detection

A bot swarm can produce a false consensus. Reputation from agreement does not stop this, because the bots agree with each other.

The engine therefore measures how frequently each pair of users agrees. A group is suspect when two conditions are true:

  • The members agree with each other on almost every target.
  • The members frequently disagree with users outside the group.

The engine decreases the reputation of each member of a suspect group. The flags of the group then have little effect on target reputation.

Open decisions

The team must answer these questions before the model is complete.

  • How does a user disagree?

    A missing flag is not a vote. The model needs an explicit signal that a label is wrong. The dispute button on a warning is one option. A “no problem here” action on pages without a warning is a second option.

  • When does a page warning become a domain warning?

    A large site collects many flags in total, even when most of its pages are acceptable. One option uses the share of flagged pages. A second option divides the flags by the number of different visitors.

  • Which weight does a new user get?

    A low start weight slows a bot swarm. It also slows honest new users.

  • How difficult is it to create an account?

    Collusion detection is weaker when one person can create many accounts at no cost. One option is authentication through an existing identity provider.

  • Who sets the first consensus?

    The first group that flags a target sets the early consensus. A bot swarm that arrives first can therefore gain reputation. A seed group of trusted users is one possible defense.

  • How much does the backend learn about browsing?

    A verdict request tells the backend which URL the user opened. The extension can request the domain only, send a hash prefix, or download the list of flagged targets.

  • Which sites get a comment adapter first?

    Each adapter is separate work. An adapter can fail when the site changes its markup.
